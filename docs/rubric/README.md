# The LeapScore rubric

This is the entry point to the rubric. Read it to learn what the rubric is, which layer owns
your question, and in what order to read.

## What an indicator is

An **indicator** is one measurable property of a codebase that predicts maintenance cost.
Each indicator has a stable ID (`ECOS-01`, `SEC-04`, …), a definition, a reason it signals
obsolescence, Yellow and Red flag criteria, an explicit four-level scoring rubric, a
remediation path, and — for rows the scanner implements — the detection recipe, fact schema,
status predicates, and evidence grammar that produce it.

An indicator is the unit of measurement. It is not a score, and it does not weight itself.

## What the rubric is

The **rubric** is the composition of the indicator set into a single grade: indicators are
grouped into categories, category grades are computed from the indicator grades, and category
grades are weighted into a system score.

```text
indicator grades (0–3, per applicable row)
        ↓  per category
category %
        ↓  weighted by category weight
system score → band (+ gate caps)
```

So the rubric is not a document separate from the indicators — it is what the indicators add
up to. The composition rules are canonical in [`model/config.md`](./model/config.md); the
grade meanings and the core-path rule are authored in [`model/scale.md`](./model/scale.md).

## What the rubric is not

- **Not the scanner.** The rubric says what is worth measuring and how a finding maps to a
  grade. The scanner implements a subset of rows and reports what it could prove; an
  unimplemented row is disclosed, never guessed.
- **Not a report.** A sealed report is one application of the rubric to one codebase at one
  time. The rubric itself carries no results.
- **Not a checklist of files.** Indicators describe properties, not required artifacts.
- **Not a place for scoring numbers to live twice.** Every weight, threshold, band, and gate
  rule has exactly one home, and the generated sheets are derived from it.

## The three layers

| Layer | Path | Owns | Edit here for |
|---|---|---|---|
| Measured set | [`indicators/`](./indicators/) | One canonical file per indicator, plus one charter per category | Indicator meaning, criteria, detection, facts, statusing, evidence, scope |
| Model | [`model/`](./model/) | How grades compose into a score: the scale and the configuration | [`scale.md`](./model/scale.md) for the 0–3 meanings and core-path rule; [`config.md`](./model/config.md) for weights, formulas, bands, gates, calibration |
| Instrument | [`sheets/`](./sheets/) | The printable and fillable sheets | **Nothing** — generated by `tooling/scripts/compile-rubric.ts` |

A document's role is carried by its directory. No scoring rule is authored outside `model/`,
and no per-indicator content is authored outside `indicators/`.

Set-level conventions — statuses, confidence, the strict N/A rule, budget classes, tool
pinning, fact naming, evidence grammar, and the full/reduced forms — live in this README
rather than in a fourth `indicators/README.md`: they apply to the whole set, so they belong
at the entry point that every audience reads first (design decision, open question resolved
here).

## The indicator file

Every canonical file carries ten sections in this order. Sections 1–4 are the rubric
semantics a reader needs to grade a row; sections 5–10 are the detector contract an
implementer needs to produce that grade. The file is one document by design — the two halves
share a single identity and must not drift apart.

| § | Section | Holds |
|---|---|---|
| 1 | Identity | ID, name, category, engine tier, default status, v1 flag, gates fed, standard/deep-dive rollup, verify effort, shared-threshold reference |
| 2 | Definition and impact | Definition, why it signals obsolescence, where it manifests, objective metric, Yellow/Red flags with rationale, example symptom, blast radius |
| 3 | Scoring semantics | The explicit 0–3 criteria for this indicator; shared numeric thresholds stay in [`model/config.md`](./model/config.md) |
| 4 | Remediation | Quick win, structural fix, gold standard, and the §1 effort tag |
| 5 | Applicability and inputs | Planes, tools and minimum versions, endpoints/rate cost, ecosystems, `na_when` predicate |
| 6 | Detection recipe | Detection intent plus ordered commands or API calls, preconditions, flags, and the no-target-code-execution rule |
| 7 | Fact schema | Indicator-namespaced facts, units, provenance, evidence pointers |
| 8 | Status and score mapping | Measured/estimated/unknown/N/A/not-implemented predicates, confidence and clamp behavior, score predicates |
| 9 | Gate, failure, and budget behavior | Gate hooks and timeout/cap/crash/rate-limit degradation/dissolve semantics |
| 10 | Evidence and output | Evidence or basis template, report-facing emission behavior, scope/overlap boundary |

### Full and reduced forms

Indicators whose surface supports a full contract use all ten sections. An indicator whose
surface cannot support a richer contract may use the approved reduced form: Identity,
report-facing emission text, and Scope/overlaps. A reduced row emits `unknown` plus an honest
"what it takes to measure" path; it must not invent a score or a fact schema.

## Conventions that apply to every indicator

These cross-indicator rules are set-level, so they live here rather than being repeated in 102
files:

1. **Statuses:** `measured`, `estimated`, `unknown`, plus `not_applicable` and
   `not_implemented` where the report contract permits them. `estimated` clamps to the
   middle of the scale and carries `confidence: low|medium`.
2. **Confidence:** `medium` requires at least two independent surfaces or exhaustive-by-
   construction coverage; otherwise `low`; never above `medium`.
3. **N/A:** `na_when` requires a structural category/archetype+plane gate or exhaustive-
   surface proof. Non-exhaustive absence is `unknown`, never N/A. Zero files are score-0 when
   the plane exists and `not_applicable` when the plane is absent.
4. **Budget classes:** `fast`, `slow-dissolvable` (sampling may become estimated +
   `scope-limited`), and `api-budgeted` (rate-limit exhaustion becomes `unknown` with a
   rate-limit path).
5. **Tool pinning:** pin the tool and its minimum major; record the exact executed version and
   flags in each fact record.
6. **Fact naming:** facts are indicator-namespaced, snake_case, and carry units in the field
   name where applicable. Predicates use only that indicator's facts.
7. **Evidence grammar:** `evidence: <tool>: <key-fact> (<path-or-endpoint>)`; estimated rows
   use `basis:`. Exactly one is emitted per row.
8. **No execution:** detectors do not run target-repository code. An execution-shaped recipe
   degrades to a static proxy or `unknown`.
9. **v1 flags:** tier A is `YES`; tier B with an approved static proxy is `PART`; otherwise
   `NO`, subject to the indicator's identity contract.

| Audit type | Duration | Scope | What to run |
|---|---|---|---|
| Portfolio screen | 1 day | All repositories | The ⚡-tagged standard rows only; skip the delivery and core-coverage gates |
| Standard audit | 2–3 days | One system | All standard rows plus all gates; FE rows folded in if a client exists |
| Deep dive | 1–2 weeks | One system | All standard and deep-dive rows (folded into categories), plus the FE module if applicable |

## Validation

Run these from the repository root. Each fails loudly rather than degrading quietly.

```bash
npm run compile:rubric              # regenerate registry + sheets from the canonical tree
npm run check:rubric-consistency    # byte-equality of generated files; no restated scoring values
npm run check:documentation-structure  # tree grammar, charters, links, citations
npm run check:schemas               # detector fact schemas resolve to a canonical indicator
```

The compiler derives the category table from the tree — order from the directory prefix, the
label from the charter heading, the category code from the indicator IDs inside it — so adding
a category means adding a directory, never editing a table.
